# Migración de Backend: PostgreSQL → MariaDB

**Fecha**: 2026-07-03
**Estado**: Diseño aprobado, pendiente de plan de implementación
**Autor**: brainstorming con el usuario

## Contexto

El hosting de producción del proyecto `cualautocompro` ofrece **solo MariaDB**, no PostgreSQL. El backend actual está implementado con:

- Node.js + Express
- Prisma ORM 5.20
- PostgreSQL como proveedor de base de datos

El usuario confirmó que el hosting **sí soporta Node.js** (VPS/Cloud con MariaDB), por lo que Prisma puede mantenerse — solo cambia el proveedor y unas pocas adaptaciones de schema/código.

## Objetivo

Migrar el backend completo de PostgreSQL a MariaDB sin perder funcionalidad, manteniendo a Prisma como ORM y asegurando que los tests y el seed sigan funcionando.

## Decisiones tomadas

| Decisión | Elección | Razón |
|---|---|---|
| Hosting | Node.js VPS/Cloud con MariaDB | Prisma sigue siendo viable |
| `galleryUrls String[]` | Campo `Json` (mapea a `LONGTEXT`) | Schema-friendly, mínima invasión |
| Migraciones existentes | Regenerar desde cero | Proyecto pre-producción, sin datos en prod |
| `extendEnum` | No-op con comentario explicativo | MariaDB no tiene enums a nivel DB |
| Enfoque general | Refactor compatible (Enfoque A) | Preserva toda la funcionalidad actual |

### 4. Raw SQL en services

Cuatro `raw query` con sintaxis PostgreSQL deben reescribirse:

**`apps/backend/src/modules/models/models.service.ts`** (líneas ~160-180 create, ~209-222 update):
- `$1, $2, ...` → `?`
- `$N::"Segment"` → `CAST(? AS CHAR)`
- `$N::text[]` (galleryUrls) → `CAST(? AS JSON)` y enviar `JSON.stringify(input.galleryUrls ?? [])`
- `NOW()` → mantener (existe en MariaDB)
- `RETURNING` → mantener (válido en MariaDB 10.5+)

**`apps/backend/src/modules/versions/versions.service.ts`** (líneas ~128-143, ~269): mismos cambios para `INSERT`/`UPDATE` de `Version`:
- `$N::"Transmission"`, `$N::"Fuel"` → `CAST(? AS CHAR)`
- `$N` → `?`

**Nota importante**: tras leer de un raw query `RETURNING`, `galleryUrls` viene como `string` (JSON serializado en LONGTEXT). Mapear con `JSON.parse(rows[0].galleryUrls) as string[]` (con try/catch que cae a `[]` ante error) **y luego pasar por `toGalleryUrls()`** para validar que sea array de strings.

### 5. Helper para `JsonValue` → `string[]`

Crear `apps/backend/src/shared/json.ts`:

```ts
import type { Prisma } from "@prisma/client";

export function toGalleryUrls(v: Prisma.JsonValue | null | undefined): string[] {
  if (Array.isArray(v)) return v.filter((x): x is string => typeof x === "string");
  if (v === null || v === undefined) return [];
  console.warn("[json] galleryUrls no es array, ignorando:", v);
  return [];
}
```

Aplicar en:
- `apps/backend/src/modules/models/models.service.ts:95-96` (`list()`, `getById()`)
- `apps/backend/src/modules/models/models.service.ts:166,215` (resultado de raw query)
- `apps/backend/src/modules/favorites/favorites.service.ts:119,147`

### 6. `extendEnum` → no-op

**`apps/backend/src/shared/enum-extension.ts`**: reemplazar la implementación PostgreSQL (`ALTER TYPE ... ADD VALUE`, `pg_enum`/`pg_type`) por un no-op que conserva solo la validación de regex:

```ts
import type { PrismaClient } from "@prisma/client";

export type EnumName = "Segment" | "Fuel" | "Transmission";

const ENUM_VALUE_REGEX = /^[A-Z0-9_]+$/;

export async function extendEnum(
  _prisma: PrismaClient,
  _enumName: EnumName,
  newValue: string,
): Promise<void> {
  if (!ENUM_VALUE_REGEX.test(newValue)) {
    throw new Error(`Valor inválido para enum ${_enumName}: ${newValue}`);
  }
  // No-op en MariaDB: Prisma mapea enums a VARCHAR sin CHECK constraint.
  // La validación contra enums vive solo en el cliente Prisma generado,
  // y se evade en los services usando raw SQL.
}
```

**`apps/backend/src/shared/enum-extension.spec.ts`**:
- **Borrar** los 2 tests que consultan `pg_enum`/`pg_type` (Postgres-only).
- **Conservar** el test de validación regex (anti-SQL-injection).
- Corregir el comentario erróneo en `beforeEach` ("pglite configurado en vitest.config.ts" — no es cierto).

## Plan de despliegue

1. Configurar MariaDB 10.5+ en hosting con charset `utf8mb4`.
2. Crear DB y usuario dedicado.
3. Actualizar `DATABASE_URL` en variables de entorno de producción.
4. `pnpm install` (regenera cliente Prisma para provider `mysql`).
5. `pnpm db:migrate deploy` (aplica migración nueva).
6. `pnpm db:seed` si aplica.
7. `pnpm build && pnpm start`.

## Criterios de aceptación

- [ ] `pnpm test` pasa contra MariaDB local.
- [ ] `pnpm db:migrate` aplica la nueva migración sin errores.
- [ ] `pnpm db:seed` puebla datos correctamente.
- [ ] `pnpm dev:be` arranca sin errores de conexión.
- [ ] Smoke test: `POST /api/models` con `galleryUrls` se persiste y se lee como array.
- [ ] `GET /api/models` devuelve `galleryUrls` como `string[]` (vía `toGalleryUrls`).
- [ ] Admin puede crear Model/Version con valores de enum "extendidos" sin errores en runtime.

## Riesgos

| ID | Severidad | Descripción | Mitigación |
|---|---|---|---|
| R1 | Media | MariaDB < 10.5 no soporta `RETURNING` | Documentar versión mínima 10.5+ en setup |
| R2 | Baja | Collation mismatch si hosting usa `utf8mb3` | Forzar `utf8mb4` en `DATABASE_URL` |
| R3 | Baja | Comportamiento de `Json` Prisma puede variar entre versiones de MariaDB | Test e2e en staging antes de prod |
| R4 | Baja | Pérdida de historial de migraciones dificulta auditoría | Aceptable para proyecto pre-producción |

## Notas de arquitectura

- **Aislamiento**: el cambio está contenido en el backend. El frontend no se toca.
- **Prisma sigue siendo la única capa de acceso a DB**: no añadimos otra abstracción.
- **SCHEMA-DRIFT NOTE**: los comentarios existentes en `models.service.ts` y `versions.service.ts` que alertan sobre drift entre raw SQL y schema deben actualizarse para reflejar que ahora también aplica a tipos de MariaDB (VARCHAR/JSON).
